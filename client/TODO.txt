=== Assistant de rebase de cheats (mise a jour de jeu, adresses qui changent) ===
Idee : apres une MAJ du jeu (nouveau build id), les offsets MAIN changent. Assistant pour
calculer le delta et réécrire les cheats existants automatiquement.

ENTREES :
- ancien fichier cheat (cheatdb E:\...\cheatdb\contents\<titleid>\cheats\<oldbuildid>.txt ou user)
- ancien dump .dmp de l'ancienne version (pour extraire les signatures) OU signature fournie
  par l'utilisateur (pattern trouve dans les 2 versions)
- nouveau dump de la session courante (deja produit par MemorySearchService) + buildid courant
  (0x11 titleid + 0x38 metadata pour le build id)

ETAPES :
1. Parser le cheat : OpCodeManager.splitLines/decodeCheatCode -> List<AOpCode>.
   Identifier les opcodes portant une adresse MAIN : 0x0 (store static), 0x5 (load fixed),
   0x1 (cond), 0xA (store, offset type 3/4/5). Les pointeurs en chaine (0x5 depuis registre)
   sont relatifs -> pas besoin de rebase. Region 4 (non-relative, adresse absolue) -> flag
   "non rebasable sans risque". HEAP : offset relatif base heap, a traiter séparément si besoin.
2. Pour chaque offset cible old : lire une fenetre de contexte (32-64 octets autour de
   main_base+offset) dans l'ancien dump (MemoryDump + DumpIndex) => signature.
3. Chercher la signature dans le dump courant, région MAIN uniquement. PATTERN SEARCH EN JAVA
   PURE sur les DumpIndex (pas besoin de la Switch) : a implementer dans le search service
   (ESearchType n'a pas encore PATTERN : ajouter ESearchType.PATTERN ou classe dediee).
4. delta = (found_addr - new_main_base) - old_offset. Prendre la MEDIANE des deltas (robuste
   aux outliers) ; signaler les cibles avec delta aberrant.
5. Re-ecrire chaque adresse (old + delta) dans les AOpCode, re-encoder via
   OpCodeManager.encodeCheatCode -> nouveau fichier <newbuildid>.txt dans cheatdb,
   ou envoi direct via 0x36 AddCheat / 0x41 SetMasterCheat.
6. Validation optionnelle : lire la valeur a la nouvelle adresse et verifier qu'elle est
   plausible (type/plage attendue).

CAS SIMPLE : si cheatdb contient deja <newbuildid>.txt -> l'utiliser directement, pas de rebase.

UI prevue : assistant wizard "Update cheats" : choisir jeu (titleid courant) -> liste les
buildids dispos dans cheatdb -> si buildid courant absent, lancer le rebase -> rapport
(delta, nb cheats ok, cheats en warning) -> enregistrer/envoyer.

=== Rebase INTERACTIF (complement) : demander la valeur affichée a l'ecran, cheat par cheat ===
Pour chaque cheat de l'ancien fichier (dans l'ordre), le wizard demande a l'utilisateur :
  "Valeur actuellement affichee a l'ecran pour [<nom du cheat>] ?"
Puis : recherche de cette valeur (ESearchType.KNOWN) dans le dump courant, de preference dans
une fenetre autour de l'ancienne adresse (old_addr +/- ex 0x10000) ou dans la region MAIN/HEAP
selon le cheat. Si plusieurs candidats :
  - prendre le plus proche de old_addr + delta median des cheats deja rebasés ;
  - sinon lister les candidats avec contexte (valeurs voisines) et laisser l'utilisateur choisir.
Si aucun candidat : demander une 2e valeur ou un pattern (signature) pour ce cheat.
Avantage : ne necessite PAS l'ancien dump (l'assistant marche juste avec l'ancien .txt +
le dump courant). C'est la methode la plus fiable quand les offsets MAIN ont glisse.
=> combine avec le mode signature : delta calcule par signatures d'abord, puis verification
   par valeurs affichees cheat par cheat (successif), avec skip possible.

=== Multi batch: rendre le batch avantageux sur les PETITES zones — A FAIRE ===

=== Commandes 0x30-0x33 converties en mode RECORD (serveur VER_PATCH 161) — FAIT ===
Principe (convention "record" comme COMMAND_STATUS/ATTACH/FREEZE) : le handler serveur n'ecrit
QUE les champs du record de sortie et retourne le rc (ecrit en trailing par le dispatcher) ;
le client fait DebuggerUtils.runCommand (writeRecord entree + readRecord sortie) puis lit un
seul readResult. DebuggerUtils supporte maintenant les tableaux en write/read (int length +
elements, recursif pour les tableaux de records).
- 0x30 : sortie RDebGetFrozenAddressesOutput(RDebFrozenAddressEntry[] entries) — serveur ecrit
  count en u32 (0 si echec) + entrees intercalees {addr u64, value u64, width u8}, plus de rc
  intermediaire. Client : getFrozenAddresses() record si >= 0x101A1, manuel (rc+count u64) sinon.
- 0x31 : entree RDebDisableFrozenAddressInput(long address), plus de rc intermediaire serveur.
  Client : unfreezeAddress() record si >= 0x101A1, manuel sinon.
- 0x32 : entree RDebReadMultiCompressedInput(int dataSize, long[] addresses) — le serveur lit
  data_size(u32) puis size(u32) puis les adresses (ordre record). La sortie reste un flux manuel
  (rc + sous-chunks RLE). Client : readmemMultiCompressedToStream choisit record vs manuel selon
  PROTOCOL_VERSION_RECORD_EXT=0x101A1.
- 0x33 : entree RDebLogMessageInput(String message) — sérialisée par EDebDataType.STRING en
  int len + octets UTF-8, RIEN ne change cote serveur (deja compatible record depuis 1.1.160),
  gate reste 0x101A0. Le cap 2048 octets reste appliqué côté client (le serveur ne lit que 2048 octets).
Client : PROTOCOL_VERSION_RECORD_EXT=0x101A1 + isRecordExtSupported(). Test : TestRecordSerde (5 tests,
round-trip write/read des records, little-endian, borne anti-desync). Serveur : VER_PATCH 161.
A rebuilder/reinstaller le sysmodule 1.1.161 pour le format record de 0x30/0x31/0x32.
REGLE : le mecanisme record ne sert QUE pour des structures de taille raisonnable en SORTIE.
readRecord borne tout tableau lu a MAX_RECORD_ARRAY_LENGTH=1_000_000 (exception AVANT allocation,
sinon OOM sur count corrompu en cas de desync). Les gros volumes (readMem 0x06/0x13/0x32) restent
en flux manuel — seule l'ENTREE de 0x32 est un record, bornee par le client (batch 64 zones max).
